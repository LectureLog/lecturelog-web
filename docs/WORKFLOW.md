# Воркфлоу разработки LectureLog (три репозитория, волнами)

Контекст для агентов. Описывает **КАК** ведётся разработка платформы и
сопутствующих правок ядра. **ЧТО** делать — в `docs/TASKS.md` (этот репо) и
`lecturelog-core/docs/TASKS-core.md` (правки ядра). **Дизайн** (почему так) — в
`docs/plans/2026-06-22-platform-design.md`.

Процесс — расширение уже обкатанного на ядре оркестратора (см.
`lecturelog-core/docs/plans/2026-06-21-orchestration-process.md`, по нему успешно
прошли 4 узла ядра). Те же роли, те же гейты, та же петля доработки — но на три
репозитория и по волнам.

---

## Главный инвариант: контракт ядра — производный от кода

`lecturelog-core/docs/openapi.json` **генерируется из кода ядра** (FastAPI),
а не пишется руками. Источник правды для платформы — этот файл, но он —
**выход** кода ядра, не вход. Отсюда жёсткий порядок:

```
код ядра → регенерация openapi.json → coreclient платформы (oapi-codegen) → код платформы
```

Поэтому **ядро патчится первым**, платформа — после стабилизации контракта.
Любая правка ядра, меняющая контракт, НЕ закрыта, пока `openapi.json`
не перегенерён, не сверен (CI `git diff --exit-code`) и не закоммичен.

## Роли агентов (как в оркестраторе ядра)

- **Оркестратор** (основная сессия): держит state-машину волны, запускает
  агентов, читает вердикты, ведёт ветки. Код руками НЕ пишет.
- **Планировщик** (Plan + writing-plans): вход — секция дизайн-документа +
  относящиеся задачи из TASKS + текущее состояние кода/контракта. Выход — `PLAN.md`.
- **Исполнитель** (general-purpose + executing-plans/TDD): код + тесты, все фазы
  до конца, в своём worktree.
- **Приёмка** (general-purpose, **НЕ исполнитель**): сверка кода с планом +
  прогон ворот (механика). Вердикт COMPLETE | INCOMPLETE + пробелы.
- **Код-ревью** (superpowers:code-reviewer): качество, баги, стандарты
  (CLAUDE.md — русские комменты, без авторства Claude; соответствие контракту
  и дизайн-документу).

## Шаблон одной задачи (атом, повторяется везде)

```
1. PLAN     планировщик → PLAN.md (в worktree, в .git/info/exclude, НЕ коммитить)
            вход: секция дизайн-документа (§N) + пункт TASKS + контракт
2. ISOLATE  свой git worktree от ветки dev репозитория
3. BUILD    исполнитель → код + тесты (TDD), все фазы
4. ACCEPT   приёмка (≠ исполнитель), двухслойно:
              слой 1 — ворота (механика, бинарно) = команды CI репо
              слой 2 — смысл по плану + инварианты дизайн-документа
            COMPLETE | INCOMPLETE
5. REVIEW   код-ревью (superpowers:code-reviewer): качество/стандарты/контракт
6. LOOP     INCOMPLETE/замечания → возврат исполнителю, тот же worktree.
            Лимит 3 круга на проверку. Застряли → СТОП, зовём человека.
            Перепроверяет тот же тип агента, что нашёл проблему.
7. MERGE    зелено (COMPLETE + APPROVE) → авто-мерж в dev репо.
8. DOCS     README/доки — ОТДЕЛЬНЫМ субагентом (правило пользователя).
```

`dev → main` в каждом репо жмёт **человек** после проверки dev-образов. Релиз
делается отдельным git-тегом `vX.Y.Z` от `main`.

## Волны (последовательность по зависимости, параллелизм — внутри волны)

```
ВОЛНА A — ЯДРО (lecturelog-core)        [4 задачи, можно ∥ в worktree-ах]
  A1 DELETE /tasks/{id}    A2 error_code    A3 structure.json    A4 lifecycle MinIO
  GATE A: регенерировать openapi.json + api-contract.md, diff-проверка,
          весь pytest зелёный, коммит контракта.  ВЫХОД = новый openapi.json
        │
        ▼
ВОЛНА B — МОСТ (lecturelog-web)         [1 задача, последовательно]
  B1 coreclient из openapi (oapi-codegen) + обёртка (HMAC, endpoints)
  GATE B: клиент компилируется (= контракт валиден) + контрактный smoke
        │
        ▼
ВОЛНА C0 — ФУНДАМЕНТ ПЛАТФОРМЫ          [последовательно, блокеры всего]
  db (схема+миграции) · web (layout «Читальный зал», Tailwind, htmx) ·
  config (.env) · auth (OAuth+сессии+CSRF/state+middleware)
  GATE C0: миграции применяются, layout рендерится, вход работает, middleware режет
        │
        ▼
ВОЛНА C1 — ДОМЕННЫЕ МОДУЛИ              [5 задач ∥ — vertical slices]
  upload · lecture · hub · reader · sync
  GATE C1: сквозной e2e — загрузка→задача в ядре→вебхук→ready→чтение→
           публикация→хаб→удаление
```

**Параллелизм** — только внутри волны и только для независимых задач (A1–A4;
C1-модули). **Последовательность** — между волнами (зависимость по
контракту/фундаменту) и внутри C0 (auth/db — раньше доменных модулей).

## Гейты-арбитры (объективные, на каждой волне)

- **GATE A** — регенерация `openapi.json` из кода + `git diff --exit-code`
  (CI-джоба openapi уже есть в ядре, краснеет при рассинхроне).
- **GATE B** — компиляция `coreclient` из openapi: если ядро отдало кривой
  контракт, здесь не соберётся ДО написания модулей платформы. Это главный
  автоловец рассинхрона.
- **GATE C0/C1** — миграции/рендер/вход и сквозной e2e.

Команды-ворота каждого репо — в его `docs/TASKS*.md` (раздел «Ворота»).

---

## Ветки и релизы

В каждом репо:

```
node/<задача> → dev → main → tag vX.Y.Z
```

- `dev` — активная разработка и быстрый prod-like чек. Каждый push в `dev`
  собирает GHCR image `:dev`.
- `main` — стабильная ветка, куда человек переносит проверенный `dev`.
- `tag vX.Y.Z` — релиз. GitHub Actions публикует Docker images `:vX.Y.Z` и
  `:latest`, затем создаёт GitHub Release.
- `latest` — только Docker-тег, не git-ветка.

Worktrees в `.worktrees/<задача>` (игнорируется), для изоляции и чистой приёмки,
не ради скорости.
