# LectureLog Web — дизайн платформы (бизнес-требования + архитектура)

> Парный документ к core-плану `lecturelog-core/docs/plans/2026-06-21-usage-tracking-design.md`
> (доработки движка). Здесь — **платформа** (`lecturelog-web`), которая строится
> поверх движка `lecturelog-core`. Документ фиксирует решения брейншторма от
> 2026-06-22 и служит опорой для разработки этого репозитория с нуля. Фронт
> детально не проектируется — вайбкодится по дизайн-системе «Читальный зал»
> (см. `design/` из дизайн-пакета).

---

## 0. Что это и для кого

Веб-платформа поверх движка генерации конспектов. Пользователь загружает
аудио/видео лекции (или YouTube-ссылку, опц. + слайды PDF), ядро генерирует
структурированный конспект, платформа даёт его читать и — по желанию —
публиковать в **общий хаб** публичных конспектов.

- Старт — **хобби/бета, биллинг ВЫКЛЮЧЕН** (тотал-фри, собираем лекции), с
  заделом на рост (подписки, докупка токенов — позже).
- **Авторизация с первого дня** (анонимных пользователей-владельцев нет).
- У каждого юзера — **личное хранилище** (приватные лекции) + возможность
  **публиковать** в хаб.

## 1. Стек и стиль

- **Go, SSR-монолит**: chi + templ + htmx + Tailwind. Фронт и бэк в одном
  сервисе, рендер на сервере, htmx-фрагменты для интерактива (поллинг статуса,
  поиск, inline-правки). Никакого JS-бандла/SPA.
- **Почему SSR, а не API+SPA** (пересмотр решения из core-плана): продукт
  контентный (чтение/каталог/публикация), дизайн уже есть в виде HTML →
  переносится в templ почти 1:1; «супер-быстрый веб» = SSR; одно развёртывание.
  Публичный JSON-API для сторонних клиентов — YAGNI, добавим слоем позже.
- Дизайн-система — **«Читальный зал»** (серив для чтения, один акцент
  `--accent`, hairline-границы, светлая/тёмная тема). Готова страница
  «Конспект», остальные экраны — по `STYLE_GUIDE.md`.

## 2. Граница с ядром (неизменная)

- **Два сервиса, один сервер**, раздельные БД, раздельные MinIO. Граница — HTTP.
- Платформа ходит в ядро **только по HTTP** и в **MinIO ядра** (презайн
  на чтение / заливка / удаление контента). **Прямого доступа к БД ядра нет** —
  ни на чтение, ни на запись. HMAC — только на вебхуке ядро→платформа (ядро
  подписывает callback, платформа верифицирует); исходящие запросы платформа→ядро
  НЕ подписываются (защита = сетевой контур + общие секреты).
- Ядро **не знает** про юзеров/права/деньги/`lecture_id` — отдаёт только физику,
  владеет своими лекциями (`results/`, `uploads/`, таблица `tasks`).
- Ядро остаётся **автономным** (работает через консоль `submit_task.py` без
  платформы).

## 3. Модель данных платформы

### users + identities (мультипровайдер-ready)
- `users`: `user_id` (uuid PK), `email` (**UNIQUE NOT NULL**), `name`,
  `avatar_url`, `created_at`. **Наш** пользователь, независим от провайдера.
- `identities`: `provider` (`'google'`), `provider_sub` (стабильный ID от
  провайдера), `user_id` FK, `created_at`. Уникальность `(provider,
  provider_sub)`. Один user → много identity. **Email в identities нет** —
  канонический email живёт в `users` (см. политику идентичности).

**Политика идентичности — email = личность:**
- Email от провайдера **и есть** идентификатор пользователя. Вход матчится
  **по email**, не по `provider_sub`.
- Логика входа: получили `{provider, provider_sub, email}` → ищем
  `users.email = email`. Нашёлся → это он, логиним и привязываем новую identity
  к существующему user (даже если зашёл другим провайдером — email тот же =
  тот же человек). Не нашёлся → новый user + identity.
- Следствие: слияние «по совпадающему email» получается **само**; разные email
  от разных провайдеров = **разные юзеры** (так и задумано).
- **Требование безопасности (анти-takeover):** матчить по email **только при
  `email_verified=true`** от провайдера. Google всегда отдаёт верифицированный
  email. Провайдеры, способные отдать неверифицированный/подменяемый email
  (напр. GitHub), **не подключаем** — допускаются только провайдеры с
  гарантированно верифицированным email. Правило держим как страховку от
  ошибки конфигурации.

### sessions (серверные сессии в Postgres)
- `sessions`: `session_id`, `user_id`, `expires_at`. Кука `session_id`
  (httponly, secure, samesite) → лукап на запрос. Настоящий logout/отзыв.
- **Redis на старте НЕ нужен** (ни ядру, ни платформе) — закрыт давний вопрос.

### lectures (тонкая обёртка над задачей ядра)
| Поле | Тип | Назначение |
|---|---|---|
| `lecture_id` | uuid PK | идентификатор платформы |
| `owner_id` | uuid FK→users | владелец |
| `core_task_id` | text, null | **текущая** задача ядра (при retry перезаписывается) |
| `status` | enum | `processing` / `ready` / `failed` (грубый ЖЦ платформы) |
| `error_code` | text, null | код ошибки от ядра при `failed` (для сообщения + права на retry) |
| `visibility` | enum | `private` / `public`, дефолт `private` (ортогонально статусу) |
| `source_kind` | enum | `audio` / `video` / `video_url` |
| `s3_key` | text, null | исходник в `uploads/` ради retry (файл); null для `video_url` |
| `video_url` | text, null | источник для retry (YouTube); null для файла |
| `title` | text | редактируемый, предзаполнен (имя файла / title видео) |
| `created_at` | timestamptz | — |
| `updated_at` | timestamptz | сортировка «недавно обновлённые», аудит смены статуса |
| `published_at` | timestamptz, null | сортировка хаба; null = не опубликована |

**Инварианты:**
- Контент лекции (markdown, медиа-фрагменты, слайды) **физически в MinIO ядра**;
  платформа хранит только метаданные+права и отдаёт контент presigned-ссылками.
- Одна лекция → одна **актуальная** core-задача. Retry создаёт новую задачу
  (новый `task_id`), `core_task_id` перезаписывается. История попыток не
  хранится (YAGNI).
- `status` и `visibility` — две ортогональные оси. Готовность ≠ публичность
  (`ready+private` валидно). Опубликовать можно только `ready`.
- **Статусный граф (направленный):** `processing → ready`, `processing →
  failed`, `failed → processing` (retry). Запись терминального статуса —
  **идемпотентный conditional update «только из processing»** (см. §7),
  гонки разрешает БД.
- Метаданные конспекта (длительность, число тем, дата) **не дублируются** —
  тянутся из результата ядра при рендере.
- Теги/таксономия хаба — **отложены** (для MVP хватит title + сортировки).

## 4. Авторизация и права

- **Вход — Google OAuth** (основной способ на старте). Бесплатно даёт
  верифицированный email, ноль хранения паролей, ноль флоу «забыл пароль».
  Мультипровайдер (только провайдеры с верифицированным email, см. §3) — потом,
  без миграции (схема `identities` готова).
- Сессия — Postgres-кука (см. §3).

### CSRF / OAuth state (MVP-критично, не отложено)
- **OAuth `state`** — безусловно. При редиректе на провайдера генерим случайный
  `state`, сохраняем (кука/сессия), на callback сверяем. Защита от CSRF на самом
  логине. Часть корректного OAuth, не опция.
- **CSRF POST-форм** — все мутирующие действия (загрузка, удаление, публикация,
  переименование, retry) идут htmx-POST'ами под куки-сессией → защищаем:
  - `SameSite=Lax` на сессионной куке (базовый щит),
  - **+ synchronizer CSRF-токен** на мутирующих формах (templ кладёт токен,
    htmx шлёт заголовком, middleware сверяет). Не полагаемся на один механизм.
  - Реализация — готовый middleware (`gorilla/csrf` / `nosurf`).
- Живёт в модуле `auth` (генерация/сверка state + CSRF-middleware на POST).

### Матрица прав
| Действие | Владелец | Другой залогиненный | Аноним |
|---|---|---|---|
| Хаб + чтение **public** | да | да | **да** |
| Чтение **private** | да | нет (404) | нет |
| presigned на контент | свои + public | public | **public** |
| Загрузка | да | да | нет (вход) |
| Публикация/снятие | свои | нет | нет |
| Удаление/переименование | свои | нет | нет |
| ЛК «Мои лекции» | свои | свои | нет |
| Retry на `failed` | свои | нет | нет |

- **Хаб и публичные конспекты открыты анонимам** (воронка привлечения:
  «зашёл с гугла → почитал → захотел свой → залогинился»). Презайн анониму
  выдаётся только на **public**-контент.
- Middleware не «стена на всё»: пропускает анонимов на public-роуты, требует
  сессию на остальном.

## 5. Загрузка лекции

Два источника, **два разных флоу** (расходятся уже на старте):

### Файл (аудио/видео) — presigned-PUT
1. Браузер → платформа: «хочу залить, имя X». Платформа берёт у ядра
   presigned-PUT (`POST /api/v1/uploads` → `uploads/<uuid>/X`), **запоминает
   выданный `s3_key`** (привязка к юзеру), отдаёт PUT-ссылку. **Карточки нет.**
2. Браузер льёт файл **напрямую в MinIO ядра** (минуя платформу). Оборвалось →
   ничего не создано; мусор чистит lifecycle ядра.
3. Браузер → платформа: «готово, `s3_key=…`». Платформа **сверяет** `s3_key`
   (я выдавала его этому юзеру?) → создаёт карточку лекции + задачу в ядре
   (`POST /tasks` с `s3_key`). Статус `processing`. Несовпадение → 403.

### YouTube-ссылка — без заливки
1. Юзер вставил ссылку → платформа **сразу** создаёт карточку + задачу в ядре с
   `video_url`. Заливать нечего, presigned нет.
2. Ядро само скачивает видео (ingestor) и обрабатывает как обычное видео.

### Опции формы
- **Переключатель режима**: файл ИЛИ YouTube-ссылка.
- **PDF слайдов** — опционально, **в обоих режимах**.
- **Тумблер «извлекать слайды из видео»** — дефолт **ВКЛ**; **гасится, если
  приложен PDF** (PDF приоритетнее — поведение ядра).
- `title` — предзаполнен (имя файла / title видео), редактируемый.

Маппинг на core: файл→`s3_key`+`media`; ссылка→`video_url`; PDF→`slides`;
тумблер-выкл→`no_slides=true`.

### Перезапуск (retry)
- Лекция `failed` (напр. rate_limit) → кнопка «Повторить» → новая задача в ядре
  из сохранённого источника (`s3_key` для файла — **в окне 7 дней** жизни
  исходника; `video_url` для ссылки — пока видео живо на YouTube).
- Карточка рождается **только после успешной заливки** → «не догрузил = нет
  карточки», битые куски чистит lifecycle.

## 6. Чтение лекции и доступ к контенту

### Presigned-политика (упрощённая, финал)
- При открытии `/lecture/L`: проверка прав → платформа **локально** подписывает
  **всю пачку** ссылок (markdown, слайды, видео, аудио) на **24 часа** →
  встраивает в HTML. Генерация подписи — без похода в MinIO, бесплатна.
- **Каждое открытие = свежая пачка** (ничего не кешируем): таймер 24ч
  обнуляется на каждый заход; права проверяются заново (снятая публикация /
  потеря доступа отражается сразу); ссылки не лежат в БД (нечему утечь).
- Видео — `<video preload="metadata">`: превью-кадр рисует **браузер** (ядро
  превью НЕ делает; платформа ffmpeg не гоняет).
- **Export ZIP** — отдельная presigned на **~60 сек** по нажатию (защита от
  пересылки: переслать живую ссылку практически нереально).
- Свойство presigned: владелец, законно получивший ссылку, может ею поделиться —
  это его право (он владелец). Посторонний ссылку **не получит** — платформа не
  выдаёт presigned без проверки прав.

### «24 часа без перезагрузки»
Длинный TTL (24ч) на пачку при открытии покрывает сессию чтения. Перезагрузка
страницы (естественный жест) = свежая пачка. Ленивая выдача/refresh —
сознательно **убраны** ради простоты беты.

### Источник структуры конспекта — `structure.json` от ядра
Дизайн «Читальный зал» рендерит **дерево** (разделы → подтемы → блоки с
тайм-кодами фрагментов и привязкой слайдов), а не плоский markdown. Ядро уже
держит это дерево в домене (`Topic`/`Section` с `start/end`, `slide_indices`,
`content`), но наружу отдаёт только Obsidian-markdown (`конспект.md`, завязан на
плагины Obsidian). Парсить его обратно в дерево — **хрупко и запрещено** дизайном.
- **Решение:** ядро дополнительно пишет `results/<task_id>/structure.json` —
  нейтральное дерево: `{source:{title,kind,duration}, sections:[{title,
  subtopics:[{title, media:{kind,start,end,key}, slide_keys:[...],
  content_md}]}]}`, где `key`/`slide_keys` — **ключи MinIO** (платформа сама
  подпишет presigned). Это **правка ядра** (§10), дешёвая — сериализация уже
  имеющегося дерева.
- **Делёж ответственности:** ядро = структура + сырой `content_md` (markdown
  секций); платформа = презентация (рендер markdown→html через goldmark,
  распознавание callout'ов, подстановка presigned). Ядро не тащит html.
- Markdown/ZIP (`конспект.md`) остаётся для кнопки «Экспорт MD» и скачивания.

### Страница чтения = «Читальный зал»
Sticky-шапка + сайдбар-оглавление (scroll-spy) + колонка контента с «лентой
времени»; медиаплееры на фрагментах, слайды+лайтбокс, callout, поиск по тексту,
экспорт MD, тема. Структура — из `structure.json`; контент секций —
markdown→html на платформе (не реконструируется из DOM).

## 7. Синхронизация статуса с ядром

- **Webhook (терминальный, HMAC)** от ядра `{task_id, status, error_code?}` →
  платформа матчит лекцию по `core_task_id` (индекс) → пишет
  `status=ready|failed` + `error_code`. Источник истины о готовности. Запоздалые
  webhook'и от устаревших (retry) задач не находят строку → игнорируются.
- **Поллинг прогресса** — htmx-фрагмент карточки опрашивает ядро
  `GET /tasks/{id}` раз в **10 сек**, **только при открытой вкладке** (живой
  прогресс стадия+%, в БД не пишется). Закрыл вкладку — поллинг встал.
- **Fallback:** поллинг, увидев `done/failed` в ядре, дописывает статус, если
  webhook потерялся. Фонового воркера нет.
- `error_code` → платформа маппит в локализованное сообщение и решает право на
  retry (`rate_limit` — да; `bad_input` — нет). **Хук под email-уведомление** —
  в обработчике терминального статуса (MVP не шлёт, точка готова).

### Конкурентность записи статуса
Webhook и поллинг-fallback — **два писателя** в одну строку `lectures`. Гонку
разрешает БД, без локов:
- Терминальный статус пишется **идемпотентным conditional update**:
  `UPDATE lectures SET status='ready' WHERE lecture_id=? AND status='processing'`.
  Кто первый перевёл `processing→ready`, второй обновит 0 строк (no-op, не ошибка).
- **Запоздалый webhook от старой (retry-нутой) задачи** отсекается двойно:
  (1) матч по `core_task_id`, а он при retry уже перезаписан → строка не
  находится; (2) даже найдись — conditional update не сработает (статус уже не
  `processing`).
- Переход `failed→processing` инициирует **только пользовательский retry**
  (одно действие, гонки нет) + ставит новый `core_task_id`.

## 8. Публикация, хаб, управление

- **Публикация** = смена флага `visibility=public` + `published_at`. Никакой
  копии — публика читает **ту же** лекцию владельца (один контент в MinIO ядра).
  Доступно только для `ready`.
- **Снятие** (`public→private`) — в любой момент; чужие доступы сразу отваливаются.
- **Хаб** = `lectures WHERE visibility=public ORDER BY published_at DESC`;
  карточка показывает **автора** (имя+аватар из OAuth).
- **Удаление** (hard delete): платформа → `DELETE /api/v1/tasks/{id}` ядру
  (ядро чистит свой MinIO `results/`/`uploads/` + строку `tasks`) → платформа
  удаляет строку `lectures`. Сначала ядро, потом своя строка (консистентность;
  при ошибке ядра свою строку не трогаем, ретраим). Удаление публичной убирает
  отовсюду.
- **Переименование** — только `title` (inline, htmx). Контент не редактируется.
- **Ядро целиком недоступно** → мягкая плашка «Сервис обработки временно
  недоступен» (502/503 экран «Читальный зал»), не 500-стектрейс.

## 9. Модульная раскладка (vertical slices)

```
platform-api/  (Go, SSR-монолит: chi + templ + htmx + Tailwind)
│
├── доменные модули (vertical slices)
│   ├── auth/     OAuth Google, сессии (Postgres-кука), users+identities, middleware прав
│   ├── upload/   форма (файл/YouTube/PDF), presigned-PUT ядра, сверка s3_key, confirm→лекция+задача
│   ├── lecture/  модель lectures, ЛК «Мои лекции», статусы, переименование, удаление, retry, visibility
│   ├── hub/      витрина публичных, список+сортировка, приманка для анонимов
│   ├── reader/   «Читальный зал»: presigned-пачка 24ч, проверка прав, рендер конспекта+медиа, export ZIP
│   └── sync/     приём webhook (HMAC, матч по core_task_id), поллинг-прокси 10с, fallback, хук email
│
└── общие слои
    ├── coreclient/  типизированный HTTP-клиент ядра (из OpenAPI ядра) + верификатор входящего вебхука ядра
    ├── s3/          локальный презайн на контент ядра, креды/endpoints MinIO ядра
    ├── db/          Postgres платформы (pgx): users, identities, sessions, lectures
    ├── web/         templ-шаблоны, layout «Читальный зал», Tailwind, статика, htmx-хелперы
    └── config/      .env: OAuth, HMAC-ключ, endpoints/креды ядра+его MinIO, callback-URL
```

**Зависимости (однонаправленно):** доменные модули → общие слои. Доменные модули
не зависят друг от друга, кроме `auth.middleware` (общий для защищённых роутов).
`sync` пишет в таблицу `lectures` через `db`, не через пакет `lecture`. Общие
слои ни от кого не зависят. Ядро спрятано за `coreclient`+`s3`.

## 10. Требования к ядру, выявленные web-гриллингом

Правки `lecturelog-core`, без которых платформа не закроет свои сценарии:

1. **`DELETE /api/v1/tasks/{task_id}`** — идемпотентный. Удаляет объекты
   `results/<task_id>/` и `uploads/<…>` в MinIO + строку `tasks` в БД ядра.
   Идемпотентность обязательна (повтор на удалённую → 2xx, не 500: платформа
   ретраит). Внутренний контракт в доверенном сетевом контуре (подпись запроса
   ядро НЕ проверяет — HMAC живёт только на вебхуке ядро→платформа). **Причина:** инкапсуляция физики —
   платформа не лезет в БД/ключи ядра, говорит «удали задачу X».
2. **`error_code` (enum)** в webhook и модели задачи — структурированный код
   вместо/в дополнение к свободному `error`. Минимум: `rate_limit` (повторяемая),
   `bad_input` (медиа битое, retry бесполезен), `internal`. Каталог кодов —
   отдельная ветка (см. §11).
3. **Lifecycle MinIO ядра** (конфиг деплоя ядра, не код платформы):
   | Правило | Prefix | Действие | Срок |
   |---|---|---|---|
   | Чистка исходников | `uploads/` | Expiration | 7 дней |
   | Чистка битых заливок | `uploads/` | AbortIncompleteMultipartUpload | 1 день |
   | `results/` | — | без правил (живёт до явного удаления) | ∞ |
4. **`structure.json` в результате** — ядро дополнительно к `конспект.md` пишет
   `results/<task_id>/structure.json`: нейтральное дерево конспекта (`source`,
   `sections → subtopics → {media:{kind,start,end,key}, slide_keys, content_md}`,
   где key/slide_keys — ключи MinIO). Сериализация уже имеющегося домена
   (`Topic`/`Section`) — дёшево. **Причина:** дизайн рендерит дерево, а не
   плоский md; парсить Obsidian-md обратно хрупко. `content_md` — markdown,
   платформа рендерит в html сама.

> Уже реализовано в ядре (подтверждено по коду): `POST /api/v1/uploads`
> (presigned-PUT, ключ `uploads/<uuid>/<file>`), приём `s3_key` в `POST /tasks`
> (инвариант «только `uploads/`, без `..`»), `video_url` источник, `no_slides`,
> приоритет PDF над видео-извлечением, presigned-GET/стрим результата,
> `results/<task_id>/result.zip`, поле `usage` в задаче.

## 11. Отложенные ветки (догрилить в будущих чатах)

1. **Каталог `error_code` ядра** — полный перечень кодов, маппинг в сообщения,
   право на retry по коду. Требует §10.2.
2. **Email-уведомления** о готовности/ошибке — fast-follow после MVP;
   переиспользует почтовую инфраструктуру. В MVP — только хук в `sync`.
3. **Poster-кадры видео** — закрыто на «нет» (превью рисует браузер через
   `preload="metadata"`); пересмотреть, если понадобятся настоящие постеры.
4. **Retry/перезапуск** — UI на `failed`, какие коды дают право, поведение при
   истёкшем 7-дневном окне исходника, лимит попыток.
5. **YouTube-ингест: операционные риски** — сбои yt-dlp (смена API ютуба,
   rate-limit/гео/возраст/приватность), нужен свой `error_code`, длинные видео.
6. **Прямой импорт MD/TeX без генерации** — конспект мимо ядра, контент в MinIO
   **платформы**, lecture без `core_task_id`. Ломает инвариант «контент в MinIO
   ядра» — отдельная ветка модели данных. Крупная фича, не MVP.
7. **Теги/таксономия хаба**, **счётчик просмотров**, **soft delete/корзина** —
   отложены как преждевременные для MVP.
8. **OpenAPI-контракт ядра** — ядро публикует `openapi.json` (см. core-план),
   платформа генерит из него типизированный `coreclient`.
9. **Биллинг** (подписки/токены) — выключен в бете; `usage` в ядре уже копится,
   платформа подключит позже.
10. **Слияние аккаунтов / привязка второго провайдера** — на старте провайдер
    один (Google), проблемы нет. Политика «email = личность» (§3) даёт слияние
    по совпадающему email автоматически; UX привязки нескольких identity к
    одному user в ЛК — отдельная ветка при добавлении второго провайдера.
